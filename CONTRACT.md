# Research Workflow Studio service contract

Python 3.9+ standard library, SQLite, HTTP and stdio MCP. See [contract-first additions](docs/contract-v3.md) for version 0.3. Research execution takes place in the user's development tools; Studio records facts and suggestions.

Research can declare optional `implementationLinks` to exact specification or code versions, with implementation/control/diagnostic roles. These purpose links are separate from actual execution and evidence use; see the [purpose-link contract](docs/contract-v3.md#declare-which-research-the-implementation-serves). Research type, execution state and human scientific judgment remain separate.

## Shared service

`rws.core.Store(db_path)` exposes `call(name, arguments, actor="model")`, `snapshot(project_id=None)` and `tool_definitions()`. `RwsError` carries `code`, `message`, optional `details`. Core is sole business writer. HTTP and stdio MCP use the same store.

- Success: `{ok:true, operation, projectId?, revision?, result, guidance?}`. Errors are structured; HTTP status maps validation/conflict/approval/not-found to 400/409/403/404.
- Every mutation needs `requestId`. A retry with identical operation+arguments+actor returns the original result. Reusing it with different payload fails. Compare canonical serialized JSON directly; no file/content hashes.
- Existing-project writes require `projectId` and `expectedRevision` (integer project revision). SQLite BEGIN IMMEDIATE, conflict check, record/history update, request result and revision increment are one transaction. No last-writer-wins.
- References are `{projectId,type,id,version?}`. `version` is integer immutable record revision, distinct from a code's display `record.version` string. Resolve and freeze omitted versions when accepting a new reference. Reject nonexistent/type-mismatched references. Historical versions remain readable.
- Supported record types: research, experiment, code, run, artifact, protocol, dataset, evaluation, comparison, analysis, report, conversation, proposal. Versioned records return `{ref,record,createdAt}`.
- `snapshot(project_id)` returns `{projects:[project],projectId,revision,records:[envelope],references:[envelope]}`. `records` contains latest own records. `references` resolves the fixed transitive references needed to display cross-project sources. Do not reinterpret old versions as latest. Project list includes all projects; no caller-global active-project state. Read-only project summaries count latest own records without changing stored revisions.
- A project has `{id,name,domain,demo,revision,activeStages,stagesConfirmedAt,versions:[{revision,at,origin,fields}],draft}`. `versions` are confirmed foundation revisions, independently numbered. Fields: goal, foundations, approach, resources, consensus. `draft` carries an exact proposal ref, baseRevision, fields, origin, at. Empty projects have no demo records.

## Operations

Read: `rws_project_list {}`, `rws_record_get {ref}`, `rws_get_context {projectId,researchRef?,experimentRef?,selectionRefs?}`. Context returns project foundation/version, position, actual objects, completed facts, pending gaps, suggestedActions with reasons and operations; it must not guess work outside registered data. Explicit research/experiment mismatch fails. An experiment keeps its bound research version; currentResearchRef/currentResearch separately expose the latest human judgment, with researchVersionNotice explaining the difference. Context is bounded to 40 object summaries, with explicit counts/truncation; full record bodies require rws_record_get. Successful mutations return a scoped guidance card within the same saved retry response.

Create: `rws_project_create {requestId,name,goal?,domain?,projectId?,demo?}`.

Records: `{requestId,projectId,expectedRevision,record}` through the specific operations below. `record.id` optional for new objects; existing records create a new version when editable. No generic write-any-type operation.

- `rws_research_save`: title, question, optional hypothesis, kind (hypothesis/exploration/reproduction), stage (idea/formal/ablation), parentRefs, optional human judgment. No automatic support/refutation; model cannot set scientific judgment.
- `rws_experiment_save`: title, researchRef, optional protocolRef, config, status. Automatically freeze current foundationRevision on creation; later edits cannot change that binding.
- `rws_code_register`: title, kind (inference/evaluation/analysis/report), version (display label), source (descriptive path/commit, not fetched), parentRefs. Code registration is immutable.
- `rws_run_register`: title, kind, codeRef (optional only for explicitly manual work), config, status (planned/running/completed/failed/partial), inputRefs, optional experimentRef. Existing run can update status, but actual code/config/input/source bindings cannot change.
- `rws_artifact_register`: title, kind, producerRef (run), sampleId?, config, uri?, availability, content? (typed result), provenance, source, description. Known provenance requires an actual non-planned producer run. A historical artifact may omit producerRef only with `provenance:"unresolved"`, nonempty source and a description of what remains unknown; never invent a producer. Producer/config/source remain immutable. Unknown/unavailable locations remain explicit; source paths do not grant file-serving access.
- `rws_protocol_register`, `rws_dataset_register`, `rws_conversation_save`: immutable typed definitions / conversation references, no automatic chat creation.
- `rws_evaluation_import`: title, protocolRef, codeRef, inputRefs, results[], status, optional experimentRef. Fixed protocol/code/input revisions. Validate typed results and metric definitions, missing/failed data, sample membership where applicable. Records existing results; does not calculate them.
- `rws_comparison_save`: title, inputRefs, fixedConditions, varyingConditions; exploration collection independent of report inputs.
- `rws_analysis_save`: title, experimentRefs, inputRefs, observations, interpretation, limitations, optional codeRef/runRef; manual analysis allowed.
- `rws_report_create_revision`: title, inputRefs, analysisRefs, evaluationRefs, researchRefs?, markdown. Freeze foundationRevision and all transitive referenced records into snapshot, never change prior report versions. The snapshot stores each exact dependency envelope once. Embedded old report snapshots replace repeated `records` bodies with `recordRefs` into that closure; the old report body, exact record versions and its original foundation remain intact. `projectFoundations` retains the foundation revisions required by cross-project experiments and reports. Flattening is storage deduplication, not rebinding historical evidence to latest records.

Usage: `rws_usage_save {requestId,projectId,expectedRevision,id?,experimentRef,artifactRefs,role,label?}` and `rws_usage_remove {requestId,projectId,expectedRevision,id}`. A usage is an explicit record in the snapshot (`type:usage`); removing/revoking it never deletes source artifacts. All uses must target an experiment in the target project; sources may belong to another project. Use `artifactRefs` to reference precise individual outputs, not dynamic groups.

Foundation: `rws_overview_propose {requestId,projectId,expectedRevision,fields,reason,sourceRefs?,baseRevision}` stores a proposal without applying it. `rws_overview_apply {requestId,projectId,expectedRevision,proposalRef,baseRevision}` is human-only and applies exactly the reviewed proposal version. Modified/stale proposal or foundation fails. `rws_overview_dismiss` similarly human-only. `rws_project_stages_set {requestId,projectId,expectedRevision,activeStages}` human-only; model can only recommend through context/proposals. Source refs are preserved. No `approved:true` bypass.

## Transports and web

- HTTP `GET /api/health`, `GET /api/state?projectId=...`, `POST /api/call {name,arguments}` (model authority), `POST /api/human/call` (human authority). GET `/api/session` returns `csrfToken` and a session cookie; human POST requires the cookie, `X-RWS-CSRF` token and matching Origin/Host. A stale session returns `session_expired` before the transaction. Browser renews the session and retries the exact operation/requestId once while retaining form input; conflicts and approval errors are not automatically retried. No wildcard CORS. Loopback binding by default; reject unsafe Host and foreign Origin. This is a single-user local trial, not an OS sandbox against processes with database access.
- Serve packaged `web/` and `GET /materials/<relative-path>` rooted exclusively at `<database parent>/materials/`. Resolve paths within that root; reject traversal, hidden path components and paths escaping it. Source metadata is never interpreted as an arbitrary readable path. Material responses stream in bounded chunks and support one byte Range (206, Content-Range, Accept-Ranges); invalid/multiple ranges return 416. PDF/image/plain-text MIME types may display inline; other types download as attachments, with nosniff and sandbox response policy. Report Markdown uses the safe renderer; raw HTML is not executed.
- MCP is newline-delimited stdio JSON-RPC with initialize/initialized, ping, tools/list, tools/call. Advertise explicit tools, safe input schemas and no shell/file-read tools. MCP always calls core with actor=model; human-only application is rejected with approval_required. CLI `mcp --db PATH --web-url http://127.0.0.1:PORT` sets the absolute review-link origin (default port 8831; HTTP loopback only), not the server listener. Encoded `projectId` plus `review=1` opens foundation review; `stages=1` opens human stage selection. Relative guidance review URLs become absolute MCP links; returning a link does not approve or execute an action.
- Browser loads real projects/records from HTTP. Preserve accepted layout, same record identity across modes. A manual refresh and revision poll may update data, but never steal selected object/view or discard dirty editors. Failed save keeps draft and displays conflict/offline status; no silent localStorage fallback presented as server success.
- Generic result kinds: metric, series, image-set, table, attachment; keep exact sample/config/source. Curves/tables are not forced into image evaluation. Cross-project display names the source project.
- The output view can select saved comparison records separately from current-experiment materials, displaying declared fixed/varying conditions. The cross-project material picker reads source projects without changing the current workspace, filters/searches and paginates artifacts, and saves exact selected versions through `rws_usage_save` to a current-project experiment. It never changes the producer or infers that matching sample names across projects mean identical inputs. Unknown producers are explicitly labelled.

## Trial acceptance

Two isolated synthetic projects exercise create/open exploration, experiment with foundation binding, actual-code run and artifacts, cross-project reference/removal, evaluation plus curve/table/image/attachment display, analysis, immutable report, model proposal then human apply, stale review rejection, duplicate request, competing writes, HTTP/MCP consistency, restart and reconnect. Explicitly mark synthetic test data. No inference/quality claim.
